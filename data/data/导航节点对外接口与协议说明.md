## 0. 阅读说明

### 0.1 证据分级

本文每条接口都标注了依据，避免把"推测"当成"契约"：

| 标记 | 含义 |
|---|---|
| ✔ | 由头文件声明、`proto` 协议定义、构建/打包脚本直接确认 |
| ◐ | 由「头文件成员名 + 名称表（`ZMQCommNameManage`）」推导，实现文件未能读取，**列在附录 B 待复核** |
| ○ | 名称表中存在，但当前 4 个节点未使用（保留能力） |

> **为什么会有 ◐**：本工作区中 4 个节点的主实现文件（`dock_lros_node.cpp`、`robot_message.cpp`、`state_*.cpp`、`nav_processor.cpp`、`nav_processor_node.cpp`、`region_manager.cpp`、`trajectory_map.cpp` 等）被 E-SafeNet 加密（文件头 `E-SafeNet ... LOCK`），无法读取明文。本文依据的是**全部可读的头文件**、**protobuf 协议**、**名称表**、**构建/打包脚本**与**已编译产物**。头文件中内联实现的接口（例如 `RobotMessage::initialize()`、各 `*StateServer::init()`）属于 ✔。

### 0.2 名称与端口的来源

1. 代码通过 `ZMQCommNameManage`（`aic-common/utils/zmq_comm_name_utils/zmq_comm_name/include/zmq_comm_name.hpp`）读取 `zmq_comm_name.yaml`；设备上的路径是 `/app/fibot/config/static_config/zmq_comm_name.yaml`，缺失时回落到头文件内置默认值。
2. 本文表格中的"名称"是 `aic-common/config/static_config/zmq_comm_name.yaml` 中的**实际配置值**（部分与头文件默认值不同，例如 `topic_nav_task_plan_path` 配置为 `task_plan_path`，默认值为 `nav_task_path`）。
3. 端口规划：

| 端口段 | 用途 |
|---|---|
| `10001` / `10002` | 话题总线的 proxy 前端 / 后端（PUB / SUB） |
| `20001` – `20030` | 服务（REQ/REP） |
| `25001` – `25012` | 动作（导航侧的动作服务） |
| `30001` – `31051` | 大包数据（图像、点云，独立 PUB 端口） |

## 2. 通信协议栈

四个节点不依赖 ROS/DDS，而是自研 **ZMQ + protobuf** 中间件（`aic-common/sdk/zmq_sdk`），对外只暴露 ZMQ 套接字语义。

### 2.1 拓扑

```text
                 ┌──────────────────────────────┐
   PUB (10001)   │        zmq_proxy_node        │   SUB (10002)
  ──────────────►│  XPUB  tcp://*:10001         │◄──────────────
                 │  XSUB  tcp://*:10002         │
                 └──────────────────────────────┘
   节点发布话题时 connect 到 10001；订阅话题时 connect 到 10002（`zmq_config.h` 的 `PUB_ADDR` / `SUB_ADDR`）

   服务：Server `bind  tcp://0.0.0.0:<port>`      Client `connect tcp://<ip>:<port>`
   大包：Publisher `bind tcp://0.0.0.0:<3xxxx>`（一个话题一个端口）
```

### 2.2 话题（topic）协议

| 项 | 约定 |
|---|---|
| 套接字 | `ZMQ_PUB` / `ZMQ_SUB` |
| 分帧 | 多帧消息：**frame0 = 话题名（原始字节）**，**frame1 = protobuf 载荷** |
| 序列化 | `SerializePartialToString()`（protobuf 二进制），反序列化为对应 `.pb.h` 类型 |
| 订阅过滤 | `setsockopt(ZMQ_SUBSCRIBE, topic_name)`，按话题名精确匹配 |
| 队列 | `advertise<T>(topic, queue_size)`；`subscribe(topic, queue_size, ...)`，`rcvhwm = queue_size` |
| 常用队列深度 | 状态类 10，结果类 1–10，TF 100 |
| 注册 | `advertise()` 会把话题名写入 `dynamic_config/registry.json`，供上位机/调试工具发现 |

### 2.3 服务（service）协议

| 项 | 约定 |
|---|---|
| 套接字 | `ZMQ_REP`（服务端 `bind`） / `ZMQ_REQ`（客户端 `connect`） |
| 载荷 | 请求、应答各为一个 protobuf 消息 |
| 超时 | 客户端默认 5000 ms（`CLIENT_RECV_TIMEOUT`），服务端 500 ms（`SERVER_RECV_TIMEOUT`） |
| 端口 | 由 `zmq_comm_name.yaml` 的 `service.*` 决定（20001–20030） |

### 2.4 动作（action）协议

本系统不使用 ROS action，而是"**REP 服务 + 结果话题**"两段式：

```text
上位机 ──<ActionGoal>──────────► <action> 服务(REP, 25xxx)
       ◄──── <ActionResponse> ──  (受理/拒绝：status + msgs)
       ◄──── <ActionResult> ──── <action>_result 话题(10001)  (执行结果)
```

* 受理应答类型统一为 `usr_define_actions::ActionResponse`（`status` / `msgs` / `error_code`）。
* 最终结果类型为 `usr_define_actions::*ActionResult`，其中 `status.status` 使用 `actionlib_msgs::ActionStatus` 语义：`SUCCEEDED` / `PREEMPTED` / `ABORTED`。
* `cmd` 字段（`usr_define_basics::ActionType`）语义：

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `ACTION_TYPE_NONE` | 空 |
| 1 | `ACTION_TYPE_START` | 启动任务 |
| 2 | `ACTION_TYPE_CANCEL` | 取消（抢占，置 `is_preempt`） |
| 3 | `ACTION_TYPE_PAUSE` | 暂停 |
| 4 | `ACTION_TYPE_CONTINUE` | 继续（若任务已结束则可重新拉起） |
| 5 | `ACTION_TYPE_FINISHED` | 任务结束 |

### 2.5 大包数据（bigdata）

* 端口段 `30001–31051`，一个话题独占一个端口，发布端 `bind`。
* 图像与点云**不走 protobuf**，使用紧凑结构体（`zmq_sdk::Image_msg`、`zmq_sdk::PointCloud2_msg`，1 字节对齐）。
* 典型话题：`fiducial_images`(30002)、`dwa_path_map_image`(30003)、`perception_docking_pointcloud`(31003)、`edge_point`(31004) 等。

### 2.6 进程健康与错误上报

每个节点在启动时构造 `MonitorBase`（`aic-common/utils/common_utils/include/monitor_base.h`）：

| 输出话题 | 类型 | 频率/时机 |
|---|---|---|
| `process_heart_beat` | `usr_define_health::ProcessHeartBeat` | 定时 2 Hz（`MONITOR_HEARTBEAT_TIME=500`） |
| `process_error_code` | `usr_define_health::ProcessErrorCode` | 事件触发（如 `ERROR_NAVIGATION_INIT = 302001`） |
| `process_exception_code` | `usr_define_health::ProcessExceptionCode` | 事件触发 |

### 2.7 坐标变换（TF）

| 话题 | 类型 | 说明 |
|---|---|---|
| `tf_static` | `tf2_msgs::TFMessage` | 静态变换，`latch=true`，队列 100 |
| `tf_dynamic` | `tf2_msgs::TFMessage` | 动态变换，队列 100 |

使用了 `tf2_ros::Buffer`/`TransformListener` 的节点会自动订阅上述两路；`RobotMessage::publishTransform()` 通过 `TransformBroadcaster` 发布 `tf_dynamic`。

## 4. 节点 `fibot_nav_dock_node`（原 `dock_lros`）

### 4.1 概述

* 一个进程内构造 4 个 `StateServer`（每个 StateServer = 1 个动作服务 + 1 个结果发布器 + 1 个任务线程；`State` 内部再起 10 Hz 工作线程）。
* 数据总线为单例 `ght_robot::RobotMessage`（`dock_lros/include/message/robot_message.h`），负责 15 路订阅与 8 路话题发布；各 `State` 通过它读写位姿、障碍、打滑、回充状态等。
* 同时创建 `costmap_2d::Costmap2DROS("local_costmap_dock")` 与 TF 监听，用于回充/沿边的局部代价地图。

### 4.2 动作服务（8 路，统一消息类型）✔

| # | 动作服务名 | 端口 | 结果话题（`AutoDockingActionResult`） | StateServer | 原节点状态 |
|---|---|---|---|---|---|
| 0 | `autodock_action` | 25001 | `autodock_action_result` | `DockStateServer` | **启用** |
| 1 | `leave_dock_action` | 25002 | `leave_dock_action_result` | `LeaveDockStateServer` | **启用** |
| 5 | `visual_egway_action` | 25005 | `visual_egway_action_result` | `VisEgwayStateServer` | **启用** |
| 6 | `egway_coverage_action` | 25006 | `egway_coverage_action_result` | `VisEgwayCoverageStateServer` | **启用** |
| 2 | `fake_bow_coverage_action` | 25003 | `fake_bow_coverage_action_result` | `FakeBowCoverageStateServer` | 注释（未注册） |
| 3 | `random_coverage_action` | 25004 | `random_coverage_action_result` | `RandomCoverageStateServer` | 注释（未注册） |
| 7 | `random_bow_coverage_action` | 25007 | `random_bow_coverage_action_result` | `RandomBowCoverageStateServer` | 注释（未注册） |
| 8 | `crossing_action` | 25008 | `crossing_action_result` | `CrossAreaStateServer` | 注释（未注册） |

> 未启用的 4 路在源码中被注释，**不会 bind 端口、不会注册结果话题**；名称仍保留在名称表中。
> 名称表另有 `to_charge_point_action`(25010)、`navigation_action`(25011)、`random_area_bow_action`(25012)，本节点未使用（供上层应用/其他机型）。

**受理规则**（`taskCallback`，各 StateServer 相同）✔

1. 运行中收到 `START`：若当前处于暂停 → 回复 `SUCCEED`（"now set to continue"），否则回复 `REJECTED`（"task is already working"）。
2. `START` 且空闲：保存 goal、唤醒任务线程，回复 `SUCCEED`。
3. `CANCEL` / `FINISHED`：置 `is_preempt`、`is_stop`，停止任务。
4. `PAUSE` / `CONTINUE`：置/清 `is_pause`；`CONTINUE` 时若任务已结束则重新拉起。
5. 其他值：回复 `UNSUPPORTED`。

**结果发布**（`executeCB`）✔：取消 → `PREEMPTED`；正常结束 → `SUCCEEDED`；异常 → `ABORTED`；`AutoDockingResult.status` 携带文字原因与耗时。

## 5. 节点 `fibot_nav_planner_node`（原 `nav_processor`）

### 5.1 概述

* 主任务节点：接收 `nav_task_action` 动作，完成全局规划（Navfn）、局部控制（DWA）、恢复行为、覆盖/沿边/重叠路径规划（IPA）。
* 进程内还构造 `CoveragePlanningServer`（IPA 覆盖规划服务端），与 `NavProcessor` 通过 ZMQ 服务交互（同进程往返）。
* 位姿来自 TF（`tf_dynamic`），不直接订阅定位话题 ✔（成员中只有 `tf_`）。

### 5.2 动作服务 ✔

| 项 | 值 |
|---|---|
| 动作服务 | `nav_task_action`（端口 25009） |

## 9. 典型时序

### 9.1 覆盖任务（COVERAGE）

```text
App ──REQ nav_task_action(25009){mode=COVERAGE, path_name}──► planner
    ◄── ActionResponse(SUCCEED)
    planner ──REQ get_grid_map(20017)──────────────► region_manager
            ◄── OccupancyGrid(area_map)
    planner ──REQ ipaCoverPath(20013, 同进程)──────► CoveragePlanningServer
            ◄── IpaGetPathResponse（覆盖路径）
    planner ──PUB nav_task_path / task_plan_path──► region_manager / App
    planner ──PUB cmd_vel─────────────────────────► 底盘
    planner ──PUB nav_status──────────────────────► 全系统
    planner ──PUB nav_task_action_result──────────► App
```

### 9.2 建图保存

```text
App ──REQ record_path(20015){command=START_MAP}──► trajectory_map
App ──PUB … 位姿/记录点 …──────────────────────────► (经 planner 周期记录)
planner ──REQ record_path{POINT, pose}───────────► trajectory_map   （2.5 s 周期）
App ──REQ record_path{SAVE_MAP}──────────────────► trajectory_map
trajectory_map ──PUB mapping_path_info───────────► region_manager
trajectory_map ──PUB trajectory_map_change───────► region_manager
region_manager ──PUB map_info / area_map─────────► App / planner
```

### 9.3 地图装载

```text
planner ──REQ map_load(20020){cmd=LOAD_WHOLE_MAP}──► region_manager
        ◄── MapLoadResponse{result, map_id_array[], path_id_array[]}
region_manager ──PUB area_map / area_edge_map / whole_map──► planner(IPA)
```

| 检查 | 方法 |
|---|---|
| 动作端口是否监听 | `ss -lntp \| grep -E '250(0[1-8])'` |
| 服务端口是否监听 | `ss -lntp \| grep -E '200(1[1-9]\|2[0-7])'` |
| 话题是否在发 | 订阅 `nav_status`、`cmd_vel` 观察频率 |
| 心跳是否正常 | 订阅 `process_heart_beat`，确认对应心跳 ID |

## 11. 变更注意事项

1. **名称改动必须同步 `zmq_comm_name.yaml`**：代码只引用字段名，实际字符串由 yaml 决定；改 yaml 会同时改变端口归属。
2. **端口不能重复绑定**：动作/服务端口为独占 `bind`，同一台设备上不能有两个进程绑定同一服务名（例如 `task_trajectory` 只能由 region_manager 提供）。
3. **动作不是 ROS action**：只订阅 `<action>_result` 而不调用动作服务的客户端永远收不到结果；反之只调服务不订阅结果也拿不到最终状态。
4. **`ActionResponse` 与 `ActionResult` 语义不同**：前者是"受理/拒绝"，后者是"执行结果"。
5. **大包话题走独立端口**：订阅 `perception_docking_pointcloud` 等必须连接对应 3xxxx 端口，而不是 10001。
